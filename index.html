System Design Blueprint

A general shape most system diagrams share: clients call a single entry point, the entry point routes to services, and services own the data. Draw the solid boxes first. Add a dashed box only when a requirement forces it.

Walk a request through it

Tracing one read and one write end to end is the fastest way to check that every box earns its place.

Read path

  1. Client sends GET /v1/items/42 with a token.
  2. Gateway checks the token and rate limit, then routes to a read-service instance.
  3. Read service checks the cache. A hit returns immediately.
  4. On a miss, it queries a read replica, fills the cache, and returns.

Write path

  1. Client sends POST /v1/items.
  2. Gateway routes to the write service, which validates the request.
  3. Write service commits to the primary DB in one transaction and invalidates the cache key.
  4. It publishes item.created and returns 201. Workers send notifications and update analytics later.

Layer checklist

What to decide at each layer, in the order you would present it.

1 · CLIENTS

Who calls the system

Decide
Client types, online vs. offline use, polling vs. push (WebSocket, SSE).
Ask
How many daily users? Read-to-write ratio? Latency target for the main screen?
2 · API DESIGN

The contract

Decide
Resources and verbs: GET /items, POST /items, PATCH /items/:id. REST, GraphQL, or gRPC.
Ask
Pagination (cursor or offset)? Idempotency keys on writes? Versioning (/v1)?
3 · EDGE / ENTRY

Load balancer + API gateway

Decide
One public entry point that handles TLS, auth, rate limits, and routing, and spreads load across instances.
Ask
Balancing strategy (round robin, least connections)? What happens when an instance fails its health check?
4 · SERVICES

Business logic

Decide
Split by domain (user, order, feed) or by read vs. write. Keep services stateless so you can add instances.
Ask
Which service owns which data? Which calls must be synchronous, and which can be events?
5 · DATA

Database

Decide
SQL for relations and transactions, NoSQL for scale and flexible shape. Define the schema and main indexes.
Ask
Strong or eventual consistency? Replicas for reads? Shard key once one node is not enough?
6 · CROSS-CUTTING

Running it

Decide
Logging, metrics, tracing, alerting. Backups and failover for the primary DB.
Ask
What is the single point of failure? What degrades gracefully when the primary is unhealthy?
