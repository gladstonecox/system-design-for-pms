Walk a Request Through It

Tracing one read and one write end to end is the fastest way to check that every box earns its place.

Read Path

  1. Client sends GET /v1/items/42 with a token.
  2. Gateway checks the token and rate limit, then routes to a read-service instance.
  3. Read service checks the cache. A hit returns immediately.
  4. On a miss, it queries a read replica, fills the cache, and returns.

Write Path

  1. Client sends POST /v1/items.
  2. Gateway routes to the write service, which validates the request.
  3. Write service commits to the primary DB in one transaction and invalidates the cache key.
  4. It publishes item.created and returns 201. Workers send notifications and update analytics later.

Interview Process

How to run the 45 minutes. This is separate from the diagram above. The diagram is the shape of the answer. This is the order you build it in. A PM round tests whether you pick the right system, prioritize requirements, and explain trade-offs. It does not test implementation detail.

  1. Understand and Scope

    Confirm the product, the users, and 2–3 core workflows. Say out loud what you are leaving out and why.

    • Functional: 3–5 things users must be able to do.
    • Non-functional: pick the 2–3 that matter most from performance, scalability, reliability, availability, consistency, security.
    • Estimate: users × actions per day = reads and writes per day. That gives the read:write ratio and flags spikes.

  2. High-Level Design

    Name the core entities, sketch the APIs, then draw boxes and arrows. Every functional requirement must show up in the diagram. Do not scale it yet.

    • Entities → APIs → data model → diagram.
    • Hello Interview budgets about 5 minutes for the API step.

  3. Deep Dive on 1–2 Flows

    Take the most important flows and show which components deliver each non-functional requirement.

    • Consistency → one atomic transaction.
    • Availability → replica or failover.
    • Performance → cache, async work.

  4. Bottlenecks and Scaling

    Zoom out and look for what breaks first.

    • Single points of failure?
    • Peak-time spikes or hot users?
    • Global users? What if traffic is 10×?

  5. Trade-Offs and Wrap-Up

    Summarize the main decisions. For each, say what you gave up and why that still serves the product. See Trade-offs.

    • Check the design against the requirements from step 1.
    • Offer one next improvement.

1. What an API Is

An API (application programming interface) is a defined set of rules that lets two pieces of software talk to each other. It says what you can ask for, how to ask, and what shape the answer comes back in. It is a contract: as long as both sides keep to it, either side can change how it works inside.

Walk it through: your browser asks the server for a list of events. That ask is an API call. The server makes its own call to the database, gets the events back, and returns them to your browser.

Three kinds of API you will meet

KindBetweenTypical protocolInterview weight
ExternalClient ↔ your backendREST (default), sometimes GraphQLThis is the one you design.
InternalService ↔ serviceRPC / gRPCOnly if the question is backend-heavy.
Real-timeClient ↔ server, kept openWebSocket, server-sent events, WebRTCOnly if a requirement needs live updates (chat, live feed).

Product lens. The API is the surface every client is built on: your web app, your mobile app, and any partner. What the API can't do, no screen can do. When you list endpoints you are really listing which user actions the product supports.

2. Anatomy of One Call

Every web API call is one request and one response, sent over HTTP.

PartWhat it isExample
Method (verb)The action: read, create, update, delete.POST
URL pathWhich resource you are acting on./v1/events
Query parametersOptional filters after ?.?city=LA
HeadersMetadata about the request. This is where the login token goes.Authorization
BodyThe data you send when creating or updating.The new event, as JSON
Status codeDid it work? 2xx success, 4xx the request was wrong, 5xx the server failed.201 Created

Product lens. Status codes decide what the user sees. A 4xx means the user can fix it: show a clear message such as "that seat is already taken" or "please log in." A 5xx means the system failed: show a retry, not blame. Good error messages are a product decision that starts in the API.

3. How an API Is Built

An API is not separate from your server. It is the set of doors the server exposes. When a request arrives, it moves through the blueprint at the top of the page:

  1. Find the server. DNS turns the domain name into the address of your entry point.
  2. Entry point. The load balancer picks a healthy instance. The API gateway checks the token, applies rate limits, and routes by path.
  3. Route to a handler. The service matches the method and path (POST /v1/events) to one function in code.
  4. Validate. Is the input well formed, and is this user allowed? If not, return a 4xx.
  5. Do the work. Read or write the database, call other services, or put a job on a queue.
  6. Respond. Build the JSON, choose a status code, send it back.

Designing an API means deciding the list of doors (endpoints), what each accepts, and what each returns. Each functional requirement maps to one or more endpoints.

Product lens. Every step costs time, and every extra call a screen needs adds a full round trip. A home screen that needs five calls loads noticeably slower on mobile than one that needs one. When latency is a requirement, ask: how many calls does the main screen need?

4. REST: Your Default

REST uses standard HTTP methods, with the things in your system represented as URLs. If you are unsure which protocol to use, choose REST. Hello Interview estimates it is right about 95% of the time.

Resources are your core entities

The nouns you named in the core-entities step become resources in the URL path. Use plural nouns, never verbs. The HTTP method carries the action.

Avoid

POST /events/create
GET  /getEvent?id=123

Prefer

POST /events
GET  /events/123
GET  /events/123/tickets

Verbs are the actions

MethodDoesExample
GETReadGET /events
POSTCreatePOST /bookings
PATCHUpdate part of somethingPATCH /events/123 with a new date
PUTReplace something entirelyPUT /events/123
DELETERemoveDELETE /events/123

Where inputs go

  • Path if it identifies the thing and is required: /events/123.
  • Query if it is an optional filter: /events?city=LA&date=2027-01-01.
  • Body if you are sending data to create or update.

Responses

On the whiteboard, write the response as the entity, GET /events → Event[], not every field. You will detail the entity in the high-level design.

Product lens. Write one endpoint per user action, and you can check coverage at a glance: every requirement should have an endpoint, and every endpoint should trace to a requirement. An endpoint with no requirement is scope creep. A requirement with no endpoint is a gap.

Going deeper: idempotency and retries

Idempotent means running the same call many times leaves the same end state. GET, PUT and DELETE are idempotent. POST is not: send POST /bookings three times and you may create three bookings. PATCH usually is.

This matters when a request times out and the client retries. For a POST that must not repeat, such as a payment or a booking, the client sends an idempotency key (a unique ID per attempt). The server sees the same key twice and returns the first result instead of charging again.

Hello Interview's advice: in interviews you will mostly use GET and POST. Don't spend time debating PUT vs. PATCH. If you are updating, PATCH is usually right. Most interviewers won't mark you down for imperfect REST naming, but plural nouns are an easy thing to get right.

5. Sync vs. Async APIs

Most calls are synchronous: the client waits, and the response carries the result. Some work takes too long to make the user wait, such as processing an uploaded video, generating a large export, or sending 10,000 invites. For those, use an asynchronous API.

Synchronous

POST /bookings
  → 201 Created + Booking

User waits a moment and sees the result.

Asynchronous

POST /exports
  → 202 Accepted + { export_id, status: "processing" }
GET  /exports/:id
  → { status: "done", download_url }

User gets an instant "we're on it," and the result arrives later.

How the client finds out it's done

  • Polling: the client asks GET /exports/:id every few seconds. Simple, wasteful.
  • Push: the server notifies the client (push notification, email, WebSocket) or, for partners, calls a webhook URL they registered.

Product lens. This decides the waiting experience. A sync call over a few seconds feels broken. An async call needs a "processing" state, a way to tell the user it's done, and a plan for failure ("your export failed, try again"). In the Calendar example, saving an event is sync, and sending invites and reminders is async, so the user isn't blocked by notifications.

6. Choosing a Protocol

SituationPickOne-line reason
Normal client-to-backend APIRESTUniversal, simple, readable. The default.
Many client types needing different data, slow mobile networks, screens that need many callsGraphQLOne request returns exactly the fields the screen needs.
Calls between your own internal servicesRPC / gRPCFaster and more compact, and you control both ends.
Public API for outside developersRESTThey already know it and need no special setup.
Chat, live scores, live feedWebSocket / SSEThe connection stays open so the server can push.

GraphQL in one sentence: instead of many fixed endpoints, the client sends one query listing exactly the fields it wants. Facebook built it in 2012 for slow mobile networks, where one screen needed several REST calls that each returned more data than the screen used.

gRPC in one sentence: internal services call each other's functions directly over a compact binary format. It is faster than REST, but both sides must share the contract, so it is a bad fit for outside clients.

Product lens. GraphQL is a mobile-performance and team-speed lever: front-end teams can build new screens without waiting for new backend endpoints. The cost is a more complex backend. gRPC is invisible to users. Mention it only if asked how services talk to each other.

Going deeper: GraphQL mechanics

With REST and several client types you either build many client-specific endpoints (sprawl) or one endpoint that returns everything (large, slow payloads). Those failures are over-fetching (more than you need) and under-fetching (needing extra calls). GraphQL answers both with one endpoint where the client picks the fields.

GraphQL: one request

POST /graphql

{
  event(id: "123") {
    name
    date
    venue { name address }
    tickets { section price available }
  }
}

REST: several requests

GET /events/123
GET /venues/45
GET /events/123/tickets

It still runs over HTTP, always as a POST to one endpoint with the query in the body, even for reads.

N+1 problem. Ask for the top 100 events plus each venue: one query for the events, then 100 more for venues, for 101 total. The fix is batching (a "data loader"): collect the venue IDs and fetch them in one query.

Field-level authorization. REST usually secures a whole endpoint. GraphQL can secure individual fields, so users can see an event's name but not its revenue.

Costs: more server complexity, harder HTTP caching, and the N+1 risk.

Going deeper: RPC and gRPC mechanics

Some backend-heavy questions have no client-facing API at all. A post-search system, for example, is mostly an indexing service, a ranking service and a logging service talking to each other. You can say there is no external API and move on, or outline the internal calls. Ask the interviewer which they prefer.

REST:  GET /events/123
RPC:   getEvent(eventId: 123)

RPC skips HTTP overhead (headers, URL parsing, JSON conversion) and sends compact binary data, usually Protocol Buffers (protobuf). The Hello Interview video says this can be 5 to 10 times faster. You define methods and message types in a file:

service TicketService {
  rpc GetEvent(GetEventRequest) returns (Event);
  rpc CreateBooking(CreateBookingRequest) returns (Booking);
}

gRPC generates typed client and server code in many languages from that file, so a Python service can call a Java service like a normal function. Outside clients still get REST, because they are diverse, need no setup, and benefit from readable JSON that passes through firewalls easily.

7. Pagination

Never return a million rows at once. That is a huge, slow response. Return a page at a time.

  • Offset (page-based): ?page=2&limit=25. Simple, and you can jump to any page. Usually the right default.
  • Cursor-based: ?cursor=<last item seen>&limit=25. Starts after the last item you received, so it stays correct when new items keep arriving.

Product lens. Match it to the UI. An infinite-scroll feed with constant new posts → cursor, or users see duplicates and gaps as they scroll. Search results or an admin table where users jump to page 7 → offset. If users report repeated items in a feed, offset pagination under heavy writes is a likely cause.

Going deeper: why offset breaks

Offset

GET /events?page=1&limit=25  → items 1–25
GET /events?page=2&limit=25  → items 26–50

Cursor

GET /events?limit=25
  → 25 events + next_cursor: "evt_025"
GET /events?limit=25&cursor=evt_025
  → the 25 after that event

If new events land above page 1 between your two requests, "items 26–50" now includes events you already saw. A cursor anchors to a specific item in a stable sort order, so inserts elsewhere can't shift your place. The cost: cursors can't jump straight to page 50.

8. Security: Who Is Calling, and What They May Do

Authentication is proving who you are. Authorization is what you are allowed to do. On a ticketing app anyone can browse events, only logged-in users can book, and only admins can create events.

Identity travels as a token in the request header, issued when the user logs in. It never comes from the body.

Avoid

POST /bookings
{ "ticket_id": "t9",
  "user_id": "42" }

Anyone could book, or tweet, or pay, as someone else by changing user_id.

Prefer

POST /bookings
Authorization: Bearer <token>
{ "ticket_id": "t9" }

Say out loud: "the server knows who I am from the token."

Mark protected endpoints as you write them, for example POST /bookings (logged in) and POST /events (admin). This is shorthand for the interviewer, not real syntax.

Rate limiting caps requests per user or key at the gateway, so one caller can't overload the system or abuse it.

Product lens. Who-can-do-what is a requirement, not an implementation detail. Roles (guest, user, admin, partner) and their permissions come from the product. Rate limits shape the experience too: set them too tight and real users hit "try again later" during a ticket drop; too loose and bots buy every seat.

Going deeper: JWT vs. session tokens
JWT (JSON Web Token)Session token
What the client sendsA JSON blob with the user's details (name, role, expiry) plus a signature.A simple ID, like a ticket number.
How the server trusts itVerifies the signature. A client can't edit its own role without breaking it.Looks the ID up in a database or cache.
CostHard to cancel before it expires.A lookup on every request. Easy to revoke.

9. Versioning and Deprecation

Once apps depend on your API, changing it can break them. Mobile makes this hard: old app versions stay installed for years, and you can't force everyone to update.

ChangeSafe?Examples
AdditiveYes. Old clients ignore what they don't know.Add a new field, a new optional parameter, a new endpoint.
BreakingNo. Needs a new version.Remove or rename a field, make an optional field required, change what a value means.

Breaking changes ship as a new version (/v2/events) while /v1 keeps running. Then you retire the old one on purpose: announce it, give a timeline, watch who still calls it, and switch it off.

Product lens. Deprecation is a product decision with real users on the other end. It needs a policy (for example, 12 months' notice for partners), usage tracking, and sometimes a forced app upgrade for very old mobile versions. In an interview, saying "I'd version the API, because old mobile clients stay in use for years" shows you think past launch day.

10. The API as a Product

When outside developers build on your API (partners, integrations, a public developer platform), the API is the product and developers are the users. Questions like "design a payments API" or "design a public API for X" are testing this.

Access and keys
Developers sign up and get an API key that identifies their app. Keys let you track usage, apply limits, and cut off abuse.
Rate limits and tiers
Limits protect the system and often double as pricing: free tier at 100 calls a minute, paid tiers higher.
Webhooks
Instead of partners polling "did anything change?", they register a URL and you call it when events happen (booking confirmed, payment failed). Less load for you, faster updates for them.
Developer experience
Clear docs, a test sandbox, readable error messages, and stable versions. These decide adoption as much as features do.
Reliability promises
Partners build businesses on you, so uptime commitments (SLAs) and status pages matter.
Metrics
Time to first successful call, active integrations, error rate by endpoint, and the slowest response times (p95/p99 latency).

Product lens. For an internal API, the users are your own teams. For a public one, every design choice is a promise you'll keep for years. Lean toward fewer, well-documented endpoints, additive change, and generous deprecation windows.

11. Worked Example: Requirements to Endpoints

Ticketing app. Start from the functional requirements, write one endpoint per user action, and note the product decision each one carries.

RequirementEndpointWhoProduct decision it carries
Browse and search eventsGET /events?city=&date= → Event[]AnyoneRead-heavy and spiky, so cache it. Paginate: offset for search results.
See an event's detailsGET /events/:id → EventAnyoneOne call should fill the whole screen. Bundle venue details in.
See available seatsGET /events/:id/tickets → Ticket[]AnyoneMust be fresh. A stale "available" seat causes failed checkouts and angry users.
Hold seats while payingPOST /bookings → Booking (status: held, expires_at)Logged inHold for 10 minutes so nobody else takes the seat mid-checkout. Show a countdown.

How to say it in the interview

"I'll use REST. Each requirement gets one endpoint. Browsing is public and cached because it's read-heavy. Booking needs a login, and it's two steps: hold the seat, then pay. That way a user never pays for a seat someone else just took, and the payment call uses an idempotency key so retries can't double-charge. Confirmation emails go out asynchronously."

12. Interview Playbook

Where this step sits

Hello Interview's framework runs: requirements → core entities → API → data flow → high-level design → deep dives. Your entities become your resources. Budget about 5 minutes. Candidates fail more often by over-detailing this step than by rushing it.

What to do, in order

  1. Take each functional requirement and write the endpoint that serves it.
  2. Say "REST" and give one reason. Mention GraphQL only if many client types or slow mobile networks are a stated concern.
  3. Write responses as entity names, not field lists.
  4. Mark which endpoints need login or a role.
  5. Call out one or two product decisions the API carries, such as async work, pagination style, or retry safety on payments.
  6. Stop, and move on to the high-level design.

Follow-ups you will get

QuestionStrong PM answer
"What if there are a million events?"Paginate. Offset for search, cursor for an infinite feed, because offset shows duplicates while new items arrive.
"How do you know who's calling?"Login token in the header. Never a user ID in the body.
"What if the payment request times out and retries?"Idempotency key, so the second attempt returns the first result instead of charging twice.
"Why REST and not GraphQL?"One web and one mobile client with similar needs. REST is simpler and caches well. I'd revisit if mobile screens needed many calls.
"This export takes two minutes."Make it async: return 202 with a status, notify the user when it's ready, handle failure.
"We need to change this response."Additive changes are safe. Breaking ones go to /v2 with a deprecation timeline, because old mobile apps stay in use.

Common mistakes

  • Endpoints that don't trace back to a requirement, or requirements with no endpoint.
  • Verbs in the URL (/createEvent).
  • A user ID in the body to identify the caller.
  • Making the user wait on slow work that could be async.
  • Listing every field, or debating PUT vs. PATCH, instead of moving on.
  • Diving into protobuf or GraphQL internals unprompted. That signals engineer depth, not product judgment.

13. Self-Check

Answer out loud, then open to check. The first five are the PM-style questions you are most likely to get.

Mobile users say the feed shows the same posts twice when they scroll. What's likely happening?

Offset pagination under heavy writes. New posts arrive above the current page, everything shifts, and the next page repeats items. Switch the feed to cursor pagination.

A user taps "Pay," the network drops, and the app retries. How do you avoid a double charge?

The client sends an idempotency key with the payment. The server sees the same key on the retry and returns the original result instead of charging again.

Generating a report takes 90 seconds. What does the API look like?

Async. POST /reports returns 202 Accepted with an ID and a "processing" status. The client polls GET /reports/:id, or the user gets a notification when it's ready. Design the failure state too.

You need to rename a field in a response. What do you do?

Renaming is a breaking change. Add the new field alongside the old one (additive), or ship it in /v2. Keep /v1 running, announce a deprecation timeline, and track who still calls it, because old mobile versions stay in use.

A partner complains they have to keep asking your API whether bookings changed. What do you offer?

Webhooks. The partner registers a URL, and you call it when a booking changes. They get updates faster and you stop serving wasted polling calls.

Why REST for clients but gRPC between services?

Clients are varied and need to work with no setup, so REST's standard HTTP and readable JSON fit. Between your own services you control both ends, so gRPC's compact, typed calls are faster.

When would you choose GraphQL over REST?

Several client types needing different data, slow mobile networks, or screens that need many REST calls. Accept a more complex backend and harder caching.

How do you stop one user booking as another?

Never trust a user ID in the body. The server identifies the caller from the login token in the header.

Component Guides

For each part: the concepts you need to design it, the trade-offs you will be asked about, and what to say. Parts follow the order of the blueprint.

Clients

Who calls the system

Core concepts

Client roles
Say what each client is for. Web handles heavier work like planning and editing. Mobile handles quick checks and reminders. Partners and bots call a public API.
DNS
The client looks up a name and gets the address of the entry point (the load balancer).
Request / response vs. real-time
Normal calls are request then response. For live updates, use polling, long-polling, WebSocket, or server-sent events.
Client-side behavior
Local caching, offline mode, optimistic UI (show the result before the server confirms).

Trade-offs

  • Polling vs. push. Polling is simple but wasteful and slightly stale. Push is instant but means holding many open connections.
  • Offline-capable vs. online-only. Offline works anywhere but needs sync and conflict handling.
  • Many client types. More reach, but old mobile versions stay in use for years, so the API must stay backward compatible.

Say: "Web is for heavy planning, mobile is for quick checks." Bring up real-time only if a requirement needs it.

API Design

The contract between client and backend

Core concepts

  • REST is the default: plural-noun resources, HTTP verbs, path / query / body inputs, 2xx / 4xx / 5xx responses.
  • GraphQL for many client types and slow networks. gRPC for service-to-service calls.
  • Pagination (offset vs. cursor) and security (token in header, never a user ID in the body) are the usual follow-ups.
  • Product decisions the API carries: sync vs. async work, versioning for old mobile apps, and partner needs like keys, rate limits and webhooks.

Trade-offs

  • REST vs. GraphQL. Simple and cacheable vs. fewer round trips but more server complexity.
  • Offset vs. cursor. Jump to any page vs. stable under heavy writes.
  • JWT vs. session token. No lookup vs. easy to revoke.

Read the full guide: API design section. Keep this step to about 5 minutes in an interview.

Edge / Entry

Load balancer, API gateway, CDN

Core concepts

Load balancer
Spreads requests across server instances and skips unhealthy ones using health checks. Common strategies are round robin and least connections.
API gateway
The single front door. Handles TLS, authentication, rate limiting, and routing each request to the right service.
Rate limiting
Caps requests per user or key so one caller can't overload the system or abuse it.
CDN
Servers spread around the world. The first request goes to the origin, then the copy is cached near users. Best for images, video, JS and CSS.
Hotspots
One server or key getting a lot more traffic than the rest, such as a celebrity's data.

Trade-offs

  • Round robin vs. least connections. Round robin is simple. Least connections adapts when requests take uneven time.
  • Gateway doing everything. One place for auth and limits, but it is another hop and a single point of failure unless you run several.
  • CDN. Much lower latency and origin load, but stale files until they expire or are purged, plus per-GB fees.
  • Rate limiting. Protects the system, but legitimate users sometimes get a 429.

Say: "Requests hit the gateway, which authenticates and rate-limits, then routes to a healthy instance."

Services

Business logic

Core concepts

Stateless
A service keeps no user state in its own memory, so any instance can serve any request and you can just add instances. State lives in the database or cache.
Horizontal vs. vertical scaling
Vertical means a bigger machine: costly, capped, still one point of failure. Horizontal means more cheap machines: needs a load balancer, but survives failures. Default to horizontal.
Break a feature into steps
Work backward from what the user sees. A Twitter timeline needs: find who you follow, fetch their tweets, score them, rank them. Each step maps to a component.
Split by domain or by read/write
Examples: a read service for viewing, a write service for create/edit/delete, plus attendee and reminder services. Say which service owns which tables.
Sync vs. async
If the user doesn't need to wait, do it after the response through a queue.
Resilience
Timeouts, retries with backoff, and degrading gracefully when a dependency is down.

Trade-offs

  • Monolith vs. microservices. A monolith is simple to build and deploy. Microservices scale and ship independently, but add network failures and operational work. Start simple.
  • Sync vs. async. Sync is simpler and the result is immediate. Async gives a fast response, but notifications and derived data arrive a moment later.
  • Separate read and write services. Reads scale on their own, but more pieces to keep in sync.
  • Retries. Recover from blips, but can cause duplicates unless the operation is idempotent.

Say: "The user gets confirmation right away. Invites and reminders are processed in the background."

Data

Modeling, storage, replication, caching

Data modeling

Four questions to answer for the data layer: What is stored? How are the entities related? Which service reads or writes each table? Which database type, and why?

Entities → tables
Each core entity becomes a table. Each row is one record. List its columns and rough types (ID, text, timestamp, status).
Primary key
The column that uniquely identifies a row, such as event_id.
Foreign key
A column that points to another table's primary key. event_id in the attendees table ties each attendee back to an event.
Relationships
One-to-many is the common case: one event has many attendees. Say it explicitly when you draw it.
Who touches what
For each table, name the service that reads it and the service that writes it. This checks that the services and tables line up.
Start simple, then layer
Version one can be text-only. When media arrives, store the file in object storage and keep only its ID in the row.
Indexes
A lookup structure on a column. It makes reads on that column fast and makes writes a little slower.
Example
Calendar: events (event_id, user_id, title, start, end, timezone), event_attendees (event_id, user_id, rsvp), reminder_jobs (reminder_id, event_id, user_id, scheduled_time, status).

Choosing and scaling the store

SQL (relational)
Tables, relationships, transactions. Use when data is tightly related and must stay consistent together. A seat purchase must charge the card and reserve the seat as one unit. Most PM questions land here.
NoSQL
Flexible shape, huge scale, very high write throughput. Use when a slightly late or out-of-order record is fine, such as activity logs.
Atomic transaction
Several writes that all commit or all roll back, so users never see a half-updated event.
Storage types
Object storage: cheap, higher latency, for files and video. Block / file: lower latency. Relational and key-value (DynamoDB, Redis) stores for structured data. Vector stores for nearest-neighbor search.
Replication
Writes go to the primary and are copied to replicas. Reads can use replicas. If the primary fails, a replica is promoted. Active-active setups let more than one node accept writes.
Caching
Fast in-memory store for data read often and changed rarely, like a leaderboard or "this week" view. Check the cache first, go to the database on a miss, and fill the cache. Decide the expiry (TTL) and the eviction rule (for example, least recently used).
Sharding
Splitting data across several databases by a shard key. Delay it until one primary can't keep up.
Consistency
Strong: everyone sees the latest write. Eventual: copies catch up shortly after.
  • SQL vs. NoSQL. SQL gives correctness across related tables. NoSQL gives scale and flexibility, but you handle relationships and consistency yourself.
  • Read replica. More read capacity and survival of a primary outage, but replication lag can show a user old data right after their own write.
  • Cache. Fast reads and lower DB load, but stale data and invalidation logic you must keep correct.
  • Strong vs. eventual consistency. Strong is trustworthy but slower and less available under failure. Eventual is fast and available, but briefly stale.
  • Normalize vs. denormalize. Normalized data has one source of truth. Denormalized data reads faster but is duplicated and can drift.
  • Sharding. Scales writes, but cross-shard queries and rebalancing are painful.

Say: "Events and attendees are tightly coupled and correctness matters, so SQL, with writes in one transaction."

Optional Components

Queue, object storage, search, analytics

Core concepts

Message queue
A producer writes a message. A consumer reads it later. They don't need to run at the same time, and each side scales on its own. Use for notifications, fan-out, retries, and absorbing spikes.
At-least-once delivery
A message can arrive twice, so consumers must be safe to repeat (idempotent). Messages that keep failing go to a dead-letter queue.
Object storage
Holds files and blobs outside the database. Metadata and the file's ID stay in the database. Often paired with a CDN.
Search index
A separate copy of data built for full-text search, fuzzy match, and filters. Kept in sync from the database, usually through events.
Analytics pipeline
Events go onto a queue, then to object storage and a data warehouse (Snowflake, Hadoop), then to business dashboards. Analytics workloads stay off the production database.

Trade-offs

  • Queue. Fast responses and buffered spikes, but eventual consistency, possible duplicates, and another system to run.
  • Object storage + CDN. Cheap and fast at scale, but an upload flow to design (often pre-signed URLs) and purge on change.
  • Search index. Real search quality, but a second copy of data that can lag the database.
  • Warehouse. Analytics without hurting users, but data is not real time.

How to Say It

Template: "We chose X because the requirement is Y. The cost is Z, which we accept because product goal."

Example: "We cache the calendar view because users check their schedule constantly and speed matters. The cost is that we have to refresh the cache whenever an event changes. In a time-sensitive product, a fast view is worth that."

Example: "Reminders and invites run asynchronously, so the user gets confirmation immediately. The cost is that an invite can arrive slightly late. Confirming the save matters more than delivering the invite in the same instant."
